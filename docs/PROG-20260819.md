## 6. DeepSeek 重试与费用风险

当前脱敏配置摘要：

- `timeout_seconds=90`；
- `max_retries=2`；
- `max_output_tokens=16384`。

因此一次解析默认最多产生 3 个独立 DeepSeek HTTP 请求：首次 1 次，加最多 2 次应用层重试。以下情况会重试：

- 网络超时或 transport error；
- HTTP 429 或 5xx；
- 200 响应但 envelope 非法或内容为空；
- 候选 JSON、Schema 或确定性语义校验失败。

401、403、普通 4xx、空输入和过长输入不会重试。当前重试没有指数退避、请求幂等键或对外尝试次数；每次重试会再次发送完整规则文本、Schema 和字段目录。

保存首个正式 draft 版本时实际记录到两次 DeepSeek HTTP 200，说明第一次结果未形成最终草稿并触发了一次重试；现有日志不足以区分具体是 envelope、空内容、JSON、Schema 还是语义问题。

同一服务请求内，只有最终校验成功结果会写 MongoDB，不会保存重试中的半成品。但客户端重复整个 `persist=true` 请求会重新解析并生成新时间戳版本，目前不能按来源内容自动去重。

如用户只要求禁止应用层自动重试，可把 `RULEREADER_DEEPSEEK_MAX_RETRIES` 设置为 `0` 并重启；在用户明确要求前不要自行修改。若要增加退避、调用审计、request idempotency 或按来源去重，必须先新建 REQ/BIZ/DEV。

## 13. JSON 向 Agent 2 交接兼容性评审

2026-08-19 按用户要求只读评审当前 JSON 是否足以支持 Agent 2 生成 SQL 模板。没有调用 DeepSeek、没有写 MongoDB、没有实现 Agent 2 或 SQL 能力。

结论：当前 JSON 便于程序解析和追溯，但不足以可靠生成 SQL 模板。Agent 2 可以读取字段并生成“看似合理”的候选 SQL，却无法仅凭当前契约确定查询参数、业务实体与粒度、结果基数、空值策略、JOIN 路径、聚合口径和元数据版本；更重要的是，当前归档 AST 自身已经存在语义丢失。

完成证据：

- 只读回查正式 MongoDB 归档版本，确认 Unicode 内容正常；此前终端中出现的乱码只是输出编码显示问题。
- `RuleParseResult` Schema 校验和当前 `validate_candidate` 均通过。
- 39 个事实中 10 个为 `mapped`、29 个为 `unresolved`；条件树 43 个节点中没有 `formula` 或 `exists`。
- 16 个事实未被条件树引用；四个条件事实没有出现在任何测试输入中。
- 来源 `R+0.1>=F` 被错误简化为 `ddgldk_total>=0`；产品 ID `759` 的两个互斥区间被放入同一个 `all` 节点。
- 简单三值诊断执行 13 个案例时，8 个与期望一致、5 个为 `INDETERMINATE`；当前校验器本身不会执行案例。

推荐的后续边界：Agent 2 不直接把整份规则 JSON 转换为一条大 SQL，而应接收按事实生成的、经过确定性校验的绑定请求；请求至少需要稳定 `factCode`、事实种类、结构化推导、实体与粒度、参数、结果契约、空值语义、规则使用位置、来源提示、元数据快照引用和事实级案例。数据库表字段、注释、索引与 JOIN 关系由后续元数据适配器提供，不应由 Agent 1 猜测。
