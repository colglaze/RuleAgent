# BUG-20260819-01：规则 AST 语义丢失未被现有校验阻止

- 状态：`TECHNICALLY_RESOLVED_BUSINESS_REVIEW_BLOCKED`
- 日期：2026-08-19
- 来源 REQ：[REQ-20260818-03](REQ-20260818-03-rule-parser.md)
- 发现于：已归档规则 JSON 向 Agent 2 交接的兼容性评审
- 影响版本：应用 `0.3.0`、Schema `1.0.0`
- 影响草稿：`REPORT_RELEASE_ALL_001@20260818T092511165521Z-562eabd40e5a`

## 现象

当前 Schema 和确定性语义校验可以接受“结构合法，但复杂公式、存在性条件或分支关系已经丢失”的模型候选。已归档《项目报告释放规则》草稿能够通过 `RuleParseResult` Schema 校验和当前 `validate_candidate` 语义校验，但不能忠实表达来源文档，也不能作为后续 Agent 2 的可靠输入。

已确认的代表性差异：

1. 来源条件 `R+0.1>=F` 被表达为单事实谓词 `ddgldk_total >= 0`，右侧 `F=B+E+C+M` 及其事实引用全部丢失。
2. 产品 ID `759` 的来源规则是 `(T<=100000 AND coverage>=70%) OR (T>100000 AND coverage>=50%)`；草稿却在同一个 `all` 节点中同时要求 `zssyjsfy<=100000` 和 `zssyjsfy>100000`，该路径逻辑上不可能成立，并且两条覆盖率公式均未进入 AST。
3. 来源中的未结束流程查询、定时释放日期计算和记录存在性判断被压缩为 `has_unfinished_flow`、`is_timed_release` 等布尔事实，但草稿没有结构化记录查询参数、事实粒度、推导依赖或存在性条件。

## 复现与证据

- 来源文件：私有 `RuleDataReferences` bundle 中的
  `sources/project-release-rules/规则agent规划/报告和数据的释放规则/项目报告释放规则.md`。
- 规范化来源 SHA-256：`562eabd40e5a5701fb9515499b542a6e2ff46056464621b1abb0a7c37f116e4d`，与归档版本一致。
- 归档草稿包含 39 个 `requiredFacts`、39 个 `fieldMappings` 和 13 个测试案例；10 个映射为 `mapped`，29 个为 `unresolved`。
- 条件树共有 43 个节点：8 个 `all`、6 个 `any`、29 个 `predicate`，没有 `formula` 或 `exists` 节点。
- 39 个 `requiredFacts` 中有 16 个没有被条件树的 `factKey` 或 `factRefs` 引用；这些事实中的多项原本应参与金额公式、合同判断或合并报告去重。
- 以缺失输入返回 `INDETERMINATE` 的简单三值诊断执行器复核 13 个草稿测试案例时，8 个与期望一致，5 个为 `INDETERMINATE`。该诊断只用于证明当前案例不足以验证 AST；正式修复必须先在 DEV 中冻结执行语义。
- 将已归档业务字段还原为 `RuleCandidate` 后，当前 `validate_candidate` 仍返回通过，说明缺陷位于现有校验能力边界内，而不是持久化损坏。

## 原因

1. `predicate` 只能表达“单个事实与字面量比较”；`formula.expression` 是未结构化字符串，缺少可确定性检查的算术表达式 AST。
2. 当前校验只保证条件和测试引用的事实存在，不保证 `requiredFacts` 与条件及推导依赖的闭包严格一致。
3. 当前校验不检查事实数据类型、操作符和值类型是否兼容。
4. 当前测试案例校验只检查至少存在一个 `pass` 和一个 `fail`、输入键已声明；不会执行条件树并核对 `expected`。
5. 当前校验不识别同一 `all` 分支内的明显互斥约束，也不能发现描述中的公式与结构字段不一致。

## 影响

- 该版本仍为 `status=draft`、`executable=false`，没有生产执行或业务状态变更影响。
- 该草稿不能通过业务审核，也不能直接交给 Agent 2 生成 SQL 模板；否则 Agent 2 可能为错误或不完整的事实定义生成看似合理的候选 SQL。
- 已有不可变版本不得覆盖或删除。修复后必须生成新版本并保留旧版本用于追溯。

## 临时约束

- 在本缺陷修复、来源规则重新解析并完成人工审核前，不把该归档版本用于 Agent 2、事实注册、规则执行或发布。
- `mapped` 只表示命中当前四视图字段目录，仍是 `reviewStatus=candidate`，不得解释为已具备可执行 SQL 模板。
- 当前阶段不实现 Agent 2、SQL 生成或执行。

## 修复验收

1. 先建立新的 REQ/BIZ/DEV，冻结面向后续事实绑定的 Schema 版本策略；若新增必填字段或改变条件表达能力，应使用新的主版本，不能原地改变 Schema `1.0.0` 的含义。
2. 使用结构化、可类型检查的表达式表示算术、比较、布尔组合、日期和存在性语义；禁止只靠描述文本保存决定性逻辑。
3. 校验条件引用与推导依赖的传递闭包，拒绝无来源的多余事实和缺失依赖。
4. 校验事实数据类型、操作符、字面量、空值策略和表达式结果类型的一致性。
5. 提供确定性规则测试执行器；所有验收案例必须得到明确的 `PASS` 或 `FAIL` 并与 `expected` 一致，不得以 `INDETERMINATE` 冒充通过。
6. 增加本缺陷的离线回归夹具，至少覆盖 `R+0.1>=F`、产品 ID `759` 两档分支、未结束流程存在性和定时释放日期边界。
7. 修复后重新解析同一来源，生成新的不可变草稿版本，并由业务人员审核事实粒度、条件树和字段映射；旧版本保持不变。
8. Ruff、Mypy 和受影响的默认离线测试通过；不以真实 DeepSeek 调用作为唯一验收证据。
