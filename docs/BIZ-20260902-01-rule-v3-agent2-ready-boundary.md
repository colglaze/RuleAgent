# BIZ-20260902-01：Rule V3 与 Agent 2 就绪边界

- 状态：`APPROVED_RECONSTRUCTED`
- 日期：2026-09-02
- 来源需求：[REQ-20260902-01](REQ-20260902-01-rule-contract-v3-agent2-ready-handoff.md)
- 恢复说明：2026-09-05 依据提交 `65a9684` 中仍可达的决策摘要和用户当前指令重建。

## 决策

1. 业务确认事实目录是 Agent 1 可用于 active 条件的唯一事实权威；规则文本、视图和模型输出只提供
   证据或候选概念，不能自行提升为确认事实。
2. 实际 XLSX 类型、枚举、空值和参数值必须原样保留；冲突进入 blocking issue，不能为通过 Schema
   而改写确认值。
3. 缺少 binding profile 时允许确认逻辑事实，但 `bindingProfileRef=null` 且必须携带
   `bindingIssues`；不得合成批准引用。
4. V3 规则结构固定五阶段并按 priority 首个命中；`postGates` 和 `exclusions` 可以降级已得到的
   `READY`。
5. 候选含业务确认缺口时停止模型纠错。模型提出的 proposed fact 不撤销已有业务确认，也不自动加入
   目录。
6. Slice 1/2 保持离线、草稿和不可执行；不构造 Agent 2 模板请求。只有无 blocking 的后续独立切片
   才可能进入 Agent 2 交接设计。
7. RuleReader 拥有业务事实语义；SqlBot 只在独立契约下消费交接、解析受治理元数据和生成待审核 SQL
   候选。SqlBot 不能清除上游 blocking，也不能把私有参考资料当作授权。
8. 私有 RuleDataReferences、视图 SQL、字段清单、工作簿和完整规则原文不复制到公开仓库；公开仓库只
   保存脱敏合成夹具和固定摘要。

## 2026-09-05 换机恢复确认

用户明确确认以下业务事实：

1. 私有 bundle 中字段清单 XLSX 已填写的数据均经过用户核对并有效；`核对状态=待补充` 是未同步更新
   的表面状态，不能据此否定已填写单元格。空白、`51`、`未标出` 等内容仍按其实际文本处理，不能
   由代码猜测缺失值。
2. V3 权威规则结构来源改为《项目报告和原始数据释放优化方案》第 1.3 节中“规则评估前依次检查、
   按优先级排序”的项目报告版本。固定规则块为 1,402 字符，SHA-256
   `f285643e5b2bb2ec7b13861716407afda4252c2fbc81eb75a4b0bb3ba4b37c6d`。
3. 详细的现行 SQL 规则、视图定义和用户后续提供的完整规则文本作为语义核对证据，不替代上述有序
   规则的阶段和优先级。
4. XLSX 与有序规则出现编码、类型或枚举不一致时，两边都保留为有效来源，生成 blocking source
   conflict；不得选择一边覆盖另一边。

## 替代与保留

本决策补充 Schema 2.0 的单一根条件表达，不修改历史 V1/V2 对象、MongoDB Schema v3 或
`FactBindingRequest 2.0.0` 的现行边界。
